# Промпт для доработки backend 2p2p.ru

Скопируй текст ниже в ИИ, которому доступен код **сервиса 2p2p.ru**. Это согласованный контракт с отправителем в ApexWebSite, а не описание уже существующего маршрута. Новый маршрут можно назвать иначе, если одновременно изменить `EMAIL_SERVICE_URL` на стороне APEX.

---

Нужно доработать мой существующий backend на **2p2p.ru**, чтобы он принимал подписанные запросы на отправку служебных писем от моего магазина **apextop.ru**. Сначала изучи структуру проекта, существующий web framework, PostgreSQL, фоновые задачи и механизм отправки писем. Реализуй это средствами проекта; не заменяй приложение и не ломай существующие endpoints. Особенно сохрани webhook заказов `/tilda/apex/webhook`: у него другое назначение.

APEX уже формирует красивое письмо, генерирует/проверяет код регистрации, ссылку восстановления, капчу, сроки действия и лимиты. Твоя задача — защищённо принять письмо, надёжно поставить его в очередь и отправить через мой Яндекс **с сервера 2p2p.ru**. Не генерируй новый код или другую ссылку, не создавай аккаунты APEX и не меняй пароли самостоятельно.

## 1. Endpoint и настройки

Создай **`POST /api/apex/email`**, доступный по **`https://2p2p.ru/api/apex/email`** без перенаправления и без обязательного завершающего слеша. Принимается только `Content-Type: application/json; charset=utf-8` (charset можно не указывать). Лимит тела — 128 КиБ. Это серверный API с HMAC-аутентификацией: браузерный CORS не нужен, cookie пользователя не являются авторизацией. Если framework использует CSRF, освободи только этот endpoint, сохранив обязательную проверку HMAC и остальную защиту приложения.

Переменные окружения backend 2p2p.ru:

```dotenv
APEX_EMAIL_SERVICE_SECRET=THE_SAME_RANDOM_SECRET_AS_ON_APEX
SMTP_HOST=smtp.yandex.com
SMTP_PORT=587
SMTP_USER=sewingnn.notification@2p2p.ru
SMTP_FROM=sewingnn.notification@2p2p.ru
SMTP_PASSWORD=YANDEX_APP_PASSWORD
```

`APEX_EMAIL_SERVICE_SECRET` на 2p2p.ru должен **в точности совпадать** с `EMAIL_SERVICE_SECRET` в APEX. Это отдельная случайная строка минимум 32 символа, рекомендуются 64 hex-символа из `secrets.token_hex(32)`. Используй её как **UTF-8 строку**, не декодируй из hex в байты. Не подставляй `STORE_MASTER_KEY`, пароль SMTP или открытый тестовый секрет. Не коммить секреты, не выводи их в логи и не проси присылать их в чат.

SMTP-пароль остаётся только на backend 2p2p.ru; магазин APEX к SMTP не подключается. Отправитель фиксирован: **`APEX <sewingnn.notification@2p2p.ru>`**. Не разрешай запросу произвольно менять From, Reply-To, список адресов, вложения или SMTP-хост. Для 587 — обязательный STARTTLS с проверкой сертификата до авторизации; для 465 — TLS с начала соединения. Ящик и пароль приложения уже настраиваются на этом сервере.

## 2. Точная проверка подписи

APEX посылает заголовки:

```text
Content-Type: application/json; charset=utf-8
Accept: application/json
User-Agent: ApexStoreMail/1
X-Apex-Timestamp: 1793000000
X-Apex-Signature: sha256=<64 lowercase hex symbols>
Idempotency-Key: apex-mail-<message_id UUID>
```

Вычисление подписи:

```python
signed_bytes = timestamp_header.encode("ascii") + b"." + raw_request_body
expected = "sha256=" + hmac.new(
    shared_secret.encode("utf-8"), signed_bytes, hashlib.sha256
).hexdigest()
valid = hmac.compare_digest(expected, signature_header)
```

- Читай **исходные байты тела** один раз с ограничением размера, **до** JSON-декодирования. Нельзя декодировать JSON и затем сериализовать его заново для проверки: порядок ключей, пробелы и UTF-8 могут отличаться.
- `X-Apex-Timestamp` — целое Unix-время в **секундах**, а не миллисекундах. Принимай отклонение от времени сервера не больше **300 секунд**. Проверь формат timestamp и `sha256=<64 hex>` до сравнения.
- Каждый повтор запроса получает свежий timestamp и подпись, но сохраняет тот же `message_id`, `Idempotency-Key` и **те же байты JSON**.
- Только после успешной подписи разбирай JSON и обрабатывай письмо. Проверяй соответствие `Idempotency-Key == "apex-mail-" + message_id`.
- Не доверяй `Origin`, `Referer`, имени домена внутри JSON или IP вместо подписи. При необходимости добавь ограничение частоты на прокси и для этого ключа, без логирования секретного содержимого.

## 3. JSON-контракт версии 1

Пример **регистрации** (данные вымышленные; даты в реальных запросах текущие):

```json
{
  "schema_version": 1,
  "message_id": "c1958709-aec3-498d-b617-917dfce16341",
  "source": "apex",
  "site_url": "https://apextop.ru",
  "kind": "registration",
  "to": "customer@example.test",
  "subject": "Подтверди почту — APEX",
  "text": "Добро пожаловать в клуб. Код: 012345. Код действует 10 минут…",
  "html": "<!doctype html><html lang=\"ru\">…готовый HTML письма от APEX…</html>",
  "created_at": "2026-10-26T12:00:00+00:00",
  "expires_at": "2026-10-26T12:10:00+00:00",
  "data": {
    "name": "Александр",
    "code": "012345"
  },
  "request_context": {}
}
```

Для **восстановления** та же структура, но:

```json
{
  "kind": "password_reset",
  "data": {
    "name": "Александр",
    "reset_url": "https://apextop.ru/account#reset-password=EXAMPLE_TOKEN"
  },
  "request_context": {
    "ip": "203.0.113.4",
    "user_agent": "Chrome / Android",
    "requested_at": "2026-10-26T12:00:00+00:00",
    "location": "Россия, Москва"
  },
  "expires_at": "2026-10-26T12:30:00+00:00"
}
```

Второй JSON показывает **отличающиеся поля**, а не отдельный сокращённый запрос: `message_id`, `to`, `subject`, `html`, `text`, `created_at`, `source`, `site_url` и `schema_version` всё равно обязательны. В JSON нет `SMTP_PASSWORD`, пароля пользователя, секрета подписи или токена Т-Банка.

Проверь схему:

- `schema_version` — целое **1**, не boolean; `source` — строго `apex`.
- `message_id` — UUID; `kind` — только `registration` или `password_reset`.
- `site_url` для production — `https://apextop.ru`; не полагайся на это поле как на аутентификацию.
- `to` — **один** email, без CR/LF, display-name, списка адресов и дополнительных заголовков; `subject` — строка до 200 символов без CR/LF. `text` и `html` — непустые строки с разумным лимитом, в пределах общего размера запроса. `data.name` — до 120 символов.
- `data.code` — строка строго из 6 цифр, **с сохранением начальных нулей**. Только для регистрации.
- `data.reset_url` — только HTTPS на точном host `apextop.ru`, без userinfo и другого порта, path `/account`, без query, fragment `reset-password=<URL-safe token>`. Не открывай эту ссылку на backend и не изменяй её. Только для восстановления. Токен — непрозрачная строка, его проверяет APEX.
- `created_at` и `expires_at` — ISO 8601 с timezone. Для нового сообщения `expires_at` должен быть в будущем, `created_at` не должен быть заметно в будущем. Нормальный TTL — 10 минут для кода и 30 минут для ссылки; для защиты от ошибочных часов допускается технический запас до 60 секунд сверх соответствующего TTL. Не продлевай срок при повторной доставке.
- В `request_context` восстановления могут быть явные сообщения «местоположение недоступно»/«отключено»: это нормально. APEX уже добавил IP, время, примерную геолокацию и предупреждение «если это не вы — игнорируйте» в HTML и текст. Не подменяй их IP-адресом сервера APEX, который прислал POST.

В production есть ровно два типа сообщений, оба транзакционные. Не превращай endpoint в открытый почтовый relay. Отправляй полученные `text` и `html` как `multipart/alternative`; дизайн уже сформирован APEX. Текст HTML не должен исполняться в админке backend без безопасного изолированного просмотра. Не загружай URL из тела запроса на сервере.

## 4. Сначала надёжная очередь, затем SMTP

- Создай миграцию для таблицы принятых писем/очереди либо используй существующую надёжную очередь с транзакционным outbox. Храни UUID, SHA-256 исходного тела, тип, срок, состояние и количество попыток. Сделай **уникальность `message_id` на уровне БД**. Дедупликации в памяти или кеша одного процесса недостаточно.
- В одной транзакции запиши зашифрованные данные письма и задачу на отправку. Если используешь RabbitMQ, исключи потерю задачи между записью БД и публикацией в RMQ: используй outbox либо подтверждённый механизм проекта. Не отвечай 202, пока задача существует только в памяти или не зафиксирована в БД.
- Повтор с тем же ID и SHA-256 тела подтверждай без создания новой задачи. Тот же ID с другим телом — **409**, без изменения исходного письма. Проверяй это и при двух одновременных POST.
- Фоновый worker берёт задачи атомарно (`FOR UPDATE SKIP LOCKED`, lease или эквивалент), повторяет временные SMTP-ошибки с backoff и восстанавливается после рестарта. Перед каждой SMTP-попыткой проверяй `expires_at`; просроченное письмо не отправляй.
- Желательно отменять ещё не отправленные старые задачи того же типа и получателя, когда принят более новый `created_at`: старый код/ссылка после нового запроса в APEX уже не действует. Уже начатую SMTP-доставку нельзя гарантированно отменить.
- Используй детерминированный SMTP `Message-ID`, например `<apex.<UUID>@2p2p.ru>`. Не обещай абсолютную однократную доставку: при потере SMTP-ответа после принятия письма возможен повтор. Но повтор HTTP-запроса **не должен создавать вторую задачу**.
- После отправки, отмены или истечения TTL очищай код, ссылку, текст и HTML. Идентификатор и SHA-256 тела для дедупликации сохраняй минимум 7 дней. Зашифрованное содержимое действующих задач должно переживать перезапуск; используй отдельный существующий ключ хранения backend, не секрет HMAC как универсальный ключ для всех целей.

## 5. Ответы, которые ожидает APEX

Успех после надёжной записи в очередь:

```http
HTTP/1.1 202 Accepted
Content-Type: application/json

{"ok":true,"message_id":"c1958709-aec3-498d-b617-917dfce16341","state":"queued"}
```

Повтор уже принятого сообщения:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"ok":true,"message_id":"c1958709-aec3-498d-b617-917dfce16341","duplicate":true}
```

Обязательны JSON **`ok: true` (именно boolean)** и **тот же `message_id`**; дополнительные поля разрешены. APEX принимает только HTTP **200 или 202** с таким JSON. Пустой ответ, HTML, `204`, `201`, перенаправление или чужой ID считаются ошибкой и вызовут повтор. 202 означает принятие задачи, не доставку во «Входящие» — SMTP-ретраи после этого полностью на стороне 2p2p.ru.

Ошибки возвращай безопасным JSON без содержимого письма, секретов и полного recipient:

- 401/403 — неверная/отсутствующая подпись или просроченный timestamp;
- 400/422 — неверные данные;
- 409 — конфликт тела для существующего ID;
- 410 — новое, уже просроченное письмо;
- 413 — превышение размера;
- 429 — лимит, можно добавить `Retry-After: 60` (секунды);
- 503 — очередь/БД временно не приняли задачу.

APEX повторяет неуспешные вызовы до истечения первоначального срока. Для 429/503 он учитывает числовой Retry-After, ограниченный 5 минутами. Не отвечай `ok:true`, если задача не сохранена. Для корректного дубликата можно ответить 200 даже если уже отправленное письмо к этому моменту истекло: новое письмо отправлять не надо.

## 6. Логи и проверки

Не логируй raw body, `data.code`, URL восстановления, HMAC-заголовки, secret, SMTP-пароль и полные тексты писем. Допустимы UUID, тип, состояние, число попыток, безопасный код ошибки и метки времени. Проверь access logs, error handlers, APM и существующее логирование webhook-body: новый endpoint не должен попадать в такие журналы. SMTP debug logging должен быть выключен.

Добавь проверки:

1. Корректно подписанные регистрация с кодом `012345` и восстановление с fragment-ссылкой принимаются; HTML и текст доставляются SMTP без смены кода/ссылки.
2. Неправильная подпись, изменённый байт тела, устаревший timestamp, пустой secret, чужой URL восстановления, несколько получателей и неизвестный тип отклоняются без отправки.
3. Два одинаковых и два параллельных POST создают одну задачу; такой же ID с другим телом даёт 409.
4. Если backend записал задачу, но клиент не получил ответ, повтор не вызывает вторую SMTP-задачу.
5. 202 возвращается только после фиксации; сбой БД не выдаёт ложный успех. Очередь восстанавливается после рестарта. Просроченные задачи очищаются без отправки.
6. Временная ошибка SMTP повторяется в фоне, постоянная ошибка видна администратору безопасным кодом; код/URL/пароль не попадают в логи.
7. Подпись проверяется по сырым байтам UTF-8 с русскими буквами и независимо от того, сколько worker-процессов запущено.

После реализации перечисли изменённые файлы, команды миграции/запуска, env, результаты тестов и безопасную проверку на моём тестовом адресе. Реальное письмо отправляй только на указанный мной тестовый адрес, после настройки секретов. Не меняй рабочий webhook заказов и не публикуй секреты.

---

После реализации этого промпта настрой на APEX `EMAIL_SERVICE_URL=https://2p2p.ru/api/apex/email` и `EMAIL_SERVICE_SECRET` с тем же значением, что `APEX_EMAIL_SERVICE_SECRET` на 2p2p.ru. На APEX `SMTP_PASSWORD` больше не нужен.
