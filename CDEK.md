# СДЭК: подключение и отправка заказов

Контракты сверены с [официальной документацией API 2.0](https://apidoc.cdek.ru/)
23 октября 2026 года. Витрина оформляет доставку в ПВЗ: отправитель самостоятельно
передаёт посылку в настроенный офис СДЭК. Нужен тариф «склад–склад», например 136
для договора интернет-магазина. Курьерские тарифы требуют адресов и отдельного
сценария оформления, которых в текущей витрине нет.

## Подключение

В админке откройте интеграции, выберите СДЭК и задайте ID/Secret, среду, тип
договора, тариф, код города и офиса отправителя. Вес задаётся в граммах,
габариты — в миллиметрах; адаптер округляет габариты вверх до сантиметров.
Для расчёта по товарам используются вес и габариты выбранных вариантов.
Перед сохранением включённой интеграции проверяются OAuth, калькулятор и
активный офис отправителя с приёмом посылок в выбранном городе и режим
выбранного тарифа «склад–склад» через список доступных тарифов.

Ключи вводятся в админке и хранятся зашифрованными. Поля `CDEK_*` из `.env`
не заменяют конфигурацию интеграции в базе. Тестовые и рабочие API разделены;
кеш токена зависит от конфигурации, после 401 токен обновляется один раз.

## Покупатель и администратор

1. Покупатель выбирает город из справочника СДЭК и действующий ПВЗ с выдачей.
2. Backend повторно проверяет наличие, цены, выбранный ПВЗ и стоимость доставки.
   При окончательном расчёте передаётся код выбранного офиса получателя.
3. После подтверждённой оплаты администратор открывает заказ и нажимает
   «Создать отправление». Передаются сохранённые товары, количество, вес,
   габариты, ФИО, телефон и email получателя, офисы отправления и получения.
4. СДЭК обрабатывает запрос асинхронно. UUID и `ACCEPTED` не считаются готовой
   накладной. Нажмите «Уточнить статус», чтобы получить результат, возможные
   ошибки и трек-номер. Номер появится также в личном кабинете покупателя.
5. «Отменить отправление» отправляет запрос отмены в СДЭК. Его результат
   также проверяется через «Уточнить статус». Отмена доставки не возвращает
   оплату и не меняет платёжный статус заказа.

Товары и доставка уже оплачены на сайте: наложенный платёж и дополнительный
сбор с получателя передаются с нулевым значением. Стоимость товарных позиций
учитывает скидки/баллы и распределение копеек между единицами товара. Вес и
габариты вариантов сохраняются вместе с заказом и не зависят от дальнейшего
редактирования товара. В режиме общего отправления вес не может быть меньше
суммарного известного веса вложений.

## API

| Действие | API магазина | API СДЭК |
| --- | --- | --- |
| Авторизация и проверка подключения | `POST /api/admin/integrations/cdek/check` | `POST /v2/oauth/token`, `POST /v2/calculator/tariff`, `POST /v2/calculator/tarifflist`, `GET /v2/deliverypoints` |
| Города России | `GET /api/delivery/cities?q=...` | `GET /v2/location/cities` |
| Пункты выдачи | `GET /api/delivery/pvz?city_code=...` | `GET /v2/deliverypoints` с `is_handout=true` |
| Расчёт | `POST /api/delivery/calculate`, `POST /api/cart/quote` | `POST /v2/calculator/tariff` |
| Создание отправления | `POST /api/admin/orders/{id}/cdek` | `POST /v2/orders` |
| Результат и трек | `GET /api/admin/orders/{id}/cdek` | `GET /v2/orders/{uuid}` |
| Восстановление результата по номеру магазина | повторное создание/проверка после таймаута | `GET /v2/orders?im_number=APEX-...` |
| Отмена отправления | `DELETE /api/admin/orders/{id}/cdek` | `DELETE /v2/orders/{uuid}` |

Административные действия требуют сессии администратора. Уведомления Т-Банка
не создают накладные: отгрузка начинается явным действием администратора после
оплаты и подготовки товара. Статусы доставки обновляются по кнопке;
автоматическая подписка на webhooks и фоновый опрос не подключены. Печатные
формы можно получить в кабинете СДЭК; печать PDF, забор курьером, международные
отправления и возвратные накладные через API не входят в текущий сценарий ПВЗ.

## Сетевые ошибки и повторные запросы

Перед запросом создания в БД фиксируется отправляемый payload и состояние
`CREATING`. Транзакционная блокировка заказа разрешает только одну попытку
создания при одновременных нажатиях. Повторная попытка для уже принятого
отправления получает состояние существующего заказа.

При таймауте или неопределённом ответе запись остаётся `UNKNOWN`/`CREATING`.
Backend не отправляет повторный `POST`: сначала ищет результат по стабильному
номеру `APEX-` + UUID заказа без дефисов (37 символов, лимит СДЭК — 40).
Если результат пока не найден, повторите проверку позднее или сверьте номер
в кабинете СДЭК. Отсутствие результата сразу после таймаута не доказывает,
что отправление не было создано. Для договора типа «Доставка» (`type=2`)
номер магазина не передаётся, поскольку он предусмотрен только для ИМ:
неопределённый результат без UUID требует ручной сверки в кабинете СДЭК.

После определённой ошибки валидации (`FAILED`/`INVALID`) доступна новая попытка
после исправления настроек. Для проверки существующего отправления нужны
исходные ID клиента и среда; смена секрета в том же аккаунте допустима.

## Проверка

Тесты проверяют формат запросов/ответов, предоплату, округление, ошибки
асинхронной валидации, восстановление после таймаута, отсутствие дублей,
защиту административных API и сохранение номера в PostgreSQL. Тесты БД
используют отдельную временную схему. Реальные отправления не создаются.
Для проверки действующего договора нужны ключи СДЭК, выбранные доступные офисы
и разрешённый сетевой доступ к API в соответствующей среде.
